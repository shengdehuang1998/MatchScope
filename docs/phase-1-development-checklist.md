# MatchScope 第一阶段开发清单与本地环境

## 1 第一阶段目标

普通用户通过 iPhone App 关注比赛、比分、盘口、预测方向和历史结果；管理员负责分析模板配置、比赛录入与维护，并可以使用手机端进行业务处理。所有数据通过真实 API 保存到 PostgreSQL。

本文统一使用“分析模板”。它是管理员配置的 AI 分析要求或上下文，系统将其与比赛资料组合后提交给 AI。代码及数据库仍使用 prompt、prompt_templates 和 prompt_versions 等英文命名。

### 1.1 业务修订与实现状态（2026-09-30）

本次文档更新定义目标与待验收要求，不代表相关代码已经实现。当前已有登录、注册、按用户归属的比赛与模板接口、手机端模板内容编辑及历史版本；尚未实现管理员与普通用户权限隔离、共享业务数据访问以及比分、盘口、预测方向的完整展示。旧流程可用不等于新业务已经验收通过。

| 能力                                         | 普通用户（user） | 管理员（admin） |
| -------------------------------------------- | ---------------- | --------------- |
| 查看可展示的比赛、比分、盘口与已生成预测方向 | 允许             | 允许            |
| 新增、编辑、取消比赛，维护比分和盘口         | 不允许           | 允许            |
| 创建、编辑名称和内容、启停与设置默认分析模板 | 不允许           | 允许            |
| 查看分析模板内容与历史版本                   | 不允许           | 允许            |
| 修改自己的邮箱、时区与通知偏好               | 允许             | 允许            |
| 配置分析排期与业务默认值                     | 不允许           | 允许            |

管理员在手机端即可完成阶段内的业务处理。Web 管理后台复用同一套服务端权限规则。管理员身份由受控服务端流程分配，不能由注册或客户端自行指定。当前已有注册代码需按阶段边界整改，无论是否开放注册，都不能允许自行成为管理员。

普通用户无需选择或查看分析模板及版本。系统自动绑定管理员配置的启用模板版本。历史版本用于追溯分析要求、关联预测记录和后续效果比较；修改模板不能覆盖已有业务记录引用的版本。

比赛及分析模板是管理员维护的业务数据，普通用户读取可展示的内容。现有按当前用户 user_id 隔离的模型与接口需要调整，并制定历史数据迁移和业务可见范围；个人设置与会话继续按用户隔离。

### 1.2 阶段闭环

管理员登录 → 配置启用的分析模板 → 维护比赛、真实比分及盘口 → 系统绑定版本并校验权限保存 → 普通用户查看比赛数据与已有预测结果。

第一阶段增加基础双角色权限、管理员移动端入口，以及比分和盘口的人工维护与真实展示。第一阶段不调用 OpenAI、不执行定时分析、不发送正式邮件。预测方向未生成时显示中文空状态，不伪造结果；AI 生成、立即分析、重新分析和第三方实时数据接入放到第二阶段。

## 2 已确定的技术框架

| 层级         | 技术                              | 第一阶段用途                        |
| ------------ | --------------------------------- | ----------------------------------- |
| 手机端       | Expo React Native TypeScript      | iPhone App 页面与交互               |
| 手机端路由   | Expo Router                       | 页面导航和路由参数                  |
| 服务端       | Node.js 24 LTS TypeScript Fastify | REST API 和业务逻辑                 |
| 数据库       | PostgreSQL                        | 保存用户 比赛 分析模板 设置和日志   |
| ORM          | Drizzle ORM                       | 数据表定义 查询和迁移               |
| 数据校验     | TypeBox JSON Schema               | API 请求 响应和共享类型             |
| Web 后台     | React Vite TypeScript             | 暂时保留 第一阶段仅作为可选调试界面 |
| 测试         | Vitest Fastify inject             | 业务规则和 API 测试                 |
| 本地基础设施 | Docker Desktop                    | 运行 PostgreSQL                     |

第一阶段采用模块化单体，不拆微服务。API 与未来的任务 Worker 共享数据库模型、业务规则和数据协议。

- [ ] 实现邮箱密码登录、Argon2id、短期 JWT、刷新令牌轮换与退出失效。
- [ ] iPhone 使用 SecureStore 保存令牌。
- [ ] 登录及 /auth/me 返回服务端角色，恢复登录后正确恢复功能入口。
- [ ] 第一阶段目标不开放公开注册；当前已有注册入口需整改，注册流程只能创建普通用户。
- [ ] 管理员身份通过受控服务端流程分配，不接受客户端自报角色。
- [ ] 后端逐接口检查角色与数据范围，禁止仅依靠前端隐藏入口。
- [ ] 角色撤销后按服务端最新身份拒绝管理操作，旧令牌不能持续保留权限。
- [ ] 登录失败使用统一中文提示，敏感接口有基础速率限制。

### 3.4 比赛管理与查看

- [ ] 管理员新增、编辑未开始比赛、取消比赛和删除无业务引用的草稿。
- [ ] 普通用户只读可展示的比赛列表、详情、比分、盘口和预测方向。
- [ ] 支持状态与日期筛选、受限分页。
- [ ] 校验联赛、主客队与开赛时间；主客队不能相同，新增排期不能是过去时间。
- [ ] 保存输入时区、UTC 时间和补充资料。
- [ ] 系统自动绑定当前启用的默认分析模板版本，普通用户不选择版本。
- [ ] 管理员修改开赛时间时增加 schedule_version。
- [ ] 管理员人工维护真实比分与盘口；比分更新使用独立规则，不能因开赛而禁止更新比分。
- [ ] 未提供比分、盘口或预测结果时显示中文缺失或未生成状态，不伪造数据。
- [ ] 普通用户接口不返回分析模板内容、内部提示词或管理配置。
- [ ] 管理操作记录操作者、对象、时间及结果。

比赛状态使用 draft、scheduled、cancelled、finished，界面映射为简体中文。分析状态、邮件状态在第二阶段独立建模，不混入比赛状态。草稿及内部管理数据不直接向普通用户展示，可见范围由服务端校验。

### 3.5 管理员分析模板管理

- [ ] 仅管理员创建、查询与编辑分析模板名称和内容。
- [ ] 支持启用、停用及默认模板设置；无可用模板时返回中文业务提示。
- [ ] 内容变更自动生成不可变版本；仅改名称或无内容变化的保存不新增内容版本。
- [ ] 管理员可查看历史版本及创建时间；已引用版本不能覆盖或删除。
- [ ] 停用模板不破坏历史引用，后续绑定使用当前启用配置。
- [ ] 手机端提供明确编辑入口，使用“保存修改”文案，版本作为管理员内部追溯功能。
- [ ] 普通用户不显示模板入口，也不能通过深链或 API 读取与修改模板。

第一阶段不实现 AI 预览。版本不作为普通用户业务操作或比赛选择条件。

### 3.8 后端 API 规范

- [ ] API 使用 /api/v1，所有业务接口要求身份认证。
- [ ] 共享 Schema 定义请求与响应，后端再次校验权限与数据范围。
- [ ] 错误响应包含稳定错误码、中文 message 和 requestId，无权限返回 403。
- [ ] 日志不记录密码、令牌或密钥，外部异常转换为中文提示。
- [ ] 提供存活检查、数据库就绪检查、OpenAPI 和分页上限。

接口权限与待实现契约：

| 接口                                                                             | 权限与用途                                     |
| -------------------------------------------------------------------------------- | ---------------------------------------------- |
| POST /auth/login、/auth/refresh、/auth/logout                                    | 身份认证与会话管理                             |
| GET /auth/me                                                                     | 返回本人身份及服务端角色                       |
| GET /matches、/matches/:id                                                       | 已登录角色读取可展示比赛，管理员按管理范围读取 |
| POST /matches、PATCH /matches/:id、POST /matches/:id/cancel、DELETE /matches/:id | 仅管理员维护业务                               |
| GET /prompts、/prompts/:id                                                       | 仅管理员读取分析模板                           |
| POST /prompts、/prompts/:id/versions、/prompts/:id/set-default                   | 仅管理员管理分析模板                           |
| PATCH /prompts/:id                                                               | 待实现：管理员修改名称及启停状态               |
| GET /settings、PATCH /settings                                                   | 本人偏好；业务排期配置需拆分或按角色限制字段   |

表中均省略 /api/v1 前缀。角色隔离、名称编辑、启停及比分/盘口维护属于待实现设计，不能据此认为现有 API 已支持；具体字段在 contracts 中定义。

## 9 本地服务和端口规划

| 服务        | 默认地址或端口          |
| ----------- | ----------------------- |
| Fastify API | `http://localhost:8187` |
| 管理后台    | `http://localhost:5174` |
| PostgreSQL  | `localhost:5432`        |
| Expo Metro  | 固定为 `8183`           |

如果真机访问本地 API，不能在 App 中使用 `localhost:8187`，因为 iPhone 的 `localhost` 指向手机本身。开发环境应使用电脑局域网 IP，例如：

```text
http://192.168.1.100:8187
```

生产环境必须使用 HTTPS 域名。

## 10 环境变量规划

仓库提交 `.env.example`，真实 `.env` 不提交 Git。

第一阶段需要：

```dotenv
NODE_ENV=development
HOST=0.0.0.0
PORT=8187
DATABASE_URL=postgresql://match_insight:match_insight@localhost:5432/match_insight
APP_TIMEZONE=Asia/Shanghai
JWT_ACCESS_SECRET=replace_with_long_random_value
ACCESS_TOKEN_TTL_MINUTES=15
REFRESH_TOKEN_TTL_DAYS=30
CORS_ORIGINS=http://localhost:5174
```

移动端只允许配置非敏感公开变量，例如：

```dotenv
EXPO_PUBLIC_API_URL=http://192.168.1.100:8187/api/v1
```

任何以 `EXPO_PUBLIC_` 开头的变量都会进入客户端构建，绝对不能放数据库密码、JWT 密钥、OpenAI 密钥或邮件密钥。

第二阶段再增加：

```dotenv
OPENAI_API_KEY=
OPENAI_MODEL=
RESEND_API_KEY=
EMAIL_FROM=
```

## 11 本地启动流程

当前仓库已经可以运行类型检查和三个原型应用：

npm install

完成第一阶段工程改造后，目标启动流程应统一为：

## 13 开发原则

长期技术架构和编码要求统一见 [技术架构与编码规范](architecture-and-coding-standards.md)。本清单保留阶段设计和待验收项，实际实现状态以代码和验收结果为准。

- 当前及后续开发功能的前端提示和用户可见文案必须统一使用简体中文，覆盖手机端和管理后台。
- 页面、按钮、状态、校验、弹窗、加载、空状态及成功与失败提示均需检查；后端业务错误及外部异常展示必须提供简体中文信息或中文兜底。

- PostgreSQL 是业务状态的唯一事实来源。
- 前端校验用于改善体验，后端必须再次校验。
- 所有时间在数据库中按 UTC 保存，界面按用户时区显示。
- 比赛、分析模板和设置只能通过 API 修改。
- 不把数据库访问代码写进路由处理函数。
- 不把业务规则写进 React 页面。
- 不覆盖已经被引用的分析模板版本。
- 不在代码和日志中出现密钥。
- 不为了未来可能的规模提前拆分微服务。
- 每完成一个模块，同时完成类型检查和核心测试。
